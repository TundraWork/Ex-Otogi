# Operations

## Deployment

One `otogi` process plus its data directory on one host, run under a supervisor (systemd, Docker, or similar) that restarts it on non-zero exit. The data directory is on local disk; SQLite WAL does not work over network filesystems.

## Configuration

- One YAML file (`otogi.yaml`; see [`otogi.example.yaml`](../otogi.example.yaml)) holds what decides whether the panel can be reached at all: the data directory, and the management API with the panel's sign-in. `GET /api/system/startup` shows these as the running process read them, with the file's path and each secret only as set or not. The other settings are edited in the control panel while the bot runs and kept in `modules.sqlite`: the general settings, the language model providers, the platform accounts, and the process settings (below), and the modules.
- Settings outside modules that are edited in the panel are grouped in sections, each kept as revisions exactly as a module's settings are: `GET /api/system` lists them, `GET /api/system/{section}/settings` returns the current revision and the JSON Schema, `PUT` saves a new revision against the `ETag` it replaces, and any earlier revision can be restored (see `docs/management-plane.md`). A saved revision of `general` or `llm` applies at once, without a restart. One of `accounts` or `process` is validated and stored, and the process runs with it from its next start: `GET /api/system` gives each section's `applies` (`now` or `restart`) and `running`, the revision the process runs with, so a restart is pending while `revision` is newer. `POST /api/restart` restarts (see [Signals and exit codes](#signals-and-exit-codes)). Every saved revision is recorded as `system.reconfigured`. A section never saved runs on its defaults.
- The `general` section (Settings, General in the panel): `operators`, the platform-qualified actor IDs (`telegram:user:123`, as `/whoami` prints them) allowed to use operator commands, which are `/status`, `/todou link`, and `/sticker` (the bot's own messages never are: the account is the bot's); `command_prefixes` (default `["/"]`; an empty list turns commands off); `eventlog_retention` (default `720h`), which the hourly prune reads each time; and `log_level` (`debug`, `info`, `warn`, `error`; default `info`). Where modules answer is chosen in the control panel.
- The `llm` section (Settings, Language models in the panel): `gemini` configures the Gemini provider with `api_key`, a reference to a secret such as `${OTOGI_GEMINI_API_KEY}`, and an optional `base_url`, the API endpoint with or without its version (default `https://generativelanguage.googleapis.com/v1beta`; a proxy or gateway that speaks the Gemini Interactions API works too). Modules name the provider and pin their own model. Saving builds every provider from the new settings and rebuilds the running modules that were built with a provider, so their next request uses the new address and key; if a provider or one of those modules does not build, nothing changes and nothing is saved. Replacing a secret a provider refers to does the same. Live tests against the API: `OTOGI_GEMINI_API_KEY=... go test -run Live -v ./internal/adapter/gemini`.
- In the `llm` section, `openai.<name>` configures a service that speaks the OpenAI Chat Completions API, such as DeepSeek, under the provider name agents use: `base_url`, the API's base without `/chat/completions` (`https://api.deepseek.com`, `https://api.openai.com/v1`), and `api_key`, a reference to a secret such as `${OTOGI_DEEPSEEK_API_KEY}`. Names are lowercase letters, digits, `-` and `_`, and not `gemini`. On DeepSeek, an agent's `web_search` and `url_context` are DeepSeek's server tools. Images go to the model as they are: pick a model that sees them. A DeepSeek model that does not (`deepseek-v4-pro`, checked 2026-11-23) answers without error but drops them, and may make up what they showed; another service may refuse every request whose history holds an image. Live tests against DeepSeek: `OTOGI_DEEPSEEK_API_KEY=... go test -run Live -v ./internal/adapter/openai`.
- The `accounts` section (Settings, Accounts): `telegram`, the Telegram user accounts, each with `account` (the name it has in events and in the paths of its files), `app_id`, `app_hash` (a reference to a secret, such as `${OTOGI_TELEGRAM_APP_HASH}`), and optionally `session`, `database`, and `upload_threads` (default 8); and `qq`, the QQ bots, each with `account`, `app_id`, `app_secret` (a reference to a secret), and optionally `database`. Saving checks the shape and that each secret is set; whether the platform accepts the credentials shows only when the driver starts. A driver that does not start stops the process, so after a restart with a wrong credential the bot is down and the panel with it: see [The bot does not start after a settings change](runbooks/control-panel.md#the-bot-does-not-start-after-a-settings-change). A new Telegram account is logged in on the server (`otogi login ACCOUNT`) after it is saved and before the restart. Replacing a secret an account refers to restarts nothing: it too is read at the next start.
- The `process` section (Settings, Process): `workers` (default 32), how many deliveries to modules run at once (a chat message with media holds one while it waits for its descriptions, up to the chat module's `describe_wait`); `max_in_flight` (default 1024), how many events may be admitted and not finished before the drivers wait; `handler_timeout` (default `10m`), the bound on one delivery for a module that sets none; `log_format` (`json` or `text`; default `json`); and `shutdown_timeout` (default `30s`). `GET /api/status` shows the workers, `max_in_flight`, and `handler_timeout_ms` the process runs with.
- `${VAR}` in any value of the file is read from the environment, which is how secrets such as the management token stay out of the file. An unset variable is an error. Use block style for such values; in flow style (`{...}`) quote them.
- `-config PATH` selects the file (default `otogi.yaml`); the first argument selects the command: `run` (default), `validate`, `login ACCOUNT`, `settings revert ID`, or `smoke`. `validate` checks the file only; the settings in the panel were checked when they were saved. `otogi login ACCOUNT` reads the accounts set in the panel.
- The whole config file is validated at startup before anything starts. Errors name the field or the line. Unknown fields are errors, so typos surface.
- Modules are not in the config file either. Which modules run and each module's settings are runtime data in `modules.sqlite`, changed through the management API: `GET /api/modules/{module}/settings` returns the current revision and the settings' JSON Schema, whose `doc` texts describe every field; `PUT` saves a new revision, which is applied at once (see `docs/management-plane.md`). A secret, such as a todou token, is never part of the settings: they hold a reference to it, `${NAME}`, resolved when the module is built. Each saved revision is recorded as `module.reconfigured`, and any earlier one can be restored.
- QQ sends names only now and then: a group member's nickname with some messages, none in private chats, and no group names. The QQ driver keeps every name a message shows. QQ's group info and member list APIs (group name, description, member count, member nicknames) are open only to whitelisted bots: the driver asks once a day per group, and when QQ refuses (code 11253), it records that once as `driver.lookup` and stops asking until restart. Name a QQ group or private chat in the panel to give it a name everywhere, agents included.
- Secrets that settings refer to, a module's or a language model provider's, are set in the control panel or through the management API (`PUT /api/secrets/{name}`), which stores them in `modules.sqlite` in the data directory, or are left in environment variables (`otogi.env`). A reference `${NAME}` takes the secret of that name set in the panel, or else the environment variable of that name; neither is an error naming the secret. Setting, replacing, or deleting one rebuilds the running modules that refer to it at once, and the language model providers that refer to it with the running modules that use a provider, and is refused, with nothing stored, if one of them does not build. Each change is recorded as `secret.changed`, without the value. Existing deployments need do nothing: a secret in `otogi.env` keeps working, and once one of the same name is set in the panel that line can be deleted. The `${VAR}` values in the config file (platform accounts, the management token, the OIDC client secret) are still read from the environment only.
- Allowlists say where modules answer: each chat agent, `bilibili`, `booth`, and `twitter` has one. The chat module also has one for each module whose tools agents may use (`tools:todou`, …): only the chats on it get that module's tools. They are runtime data in `modules.sqlite`, not config, changed in the control panel or through the management API; each change is recorded as `allowlist.changed`. So is each module's "ignore bots" switch (on unless turned off: messages from bot accounts do not reach the module), recorded as `bots.changed`.
- The `bilibili`, `booth`, and `twitter` modules answer Bilibili video links (`bilibili.com/video/…`, `b23.tv/…`), Booth items (`booth.pm/…/items/…` and shop domains such as `shop.booth.pm/items/…`), and X posts (`x.com/…/status/…`, `twitter.com`, and the fxtwitter/vxtwitter/fixupx mirrors) in the chats on their allowlists with a card image drawn by Chrome; `twitter` also takes a `timezone` (IANA name) for its times, `videos` (send a post's videos and GIFs after its card; default on) and `max_video_mb` (the largest one sent; default 50), and `translate` (`provider`, `model`, `thinking`): a language model then reads each post with text, and when it is not in Chinese the card also shows it translated into Simplified Chinese under the original, marked with who translated it from what; the post's quote, the post it replies to, and that post's quote are translated the same way, each in its own request to the model (so a reply that quotes costs up to four), under its original and only when it is not in Chinese. A reply costs one more look-up, for the post it replies to. The card then waits for the translation. How they censor pictures is the `safety` module's (Content safety in the panel): how far sensitive pictures are blurred (`blur`, default 9; 0 for none), whether a refused card goes out again under a sticker (`cover_refused`, default on), and the sticker (`sticker`, an image file on the server, default the built-in one; `sticker_opacity`, default 0.65; `sticker_size`, default 66 percent), and whether the videos of a post whose pictures are censored are sent anyway (`censored_videos`, default off). BOOTH and X cards need it on. How much each card module answers and shows is its settings: `max_videos` (bilibili), `max_items`, `max_options`, and `max_tags` (booth), and `max_posts`, `max_text`, and `max_quote_text` (twitter). `booth` and `twitter` need `chrome`, and `bilibili` uses it when it is set (without it, a Bilibili card goes out in words, with the cover): the path of a pinned [chrome-headless-shell](https://googlechromelabs.github.io/chrome-for-testing/) (`linux64` build, unzipped anywhere readable by the service user), its shared libraries, and fonts. On Ubuntu 24.04: `apt-get install --no-install-recommends libnspr4 libnss3 libatk1.0-0t64 libatk-bridge2.0-0t64 libxcomposite1 libxdamage1 libxfixes3 libxrandr2 libgbm1 libasound2t64 libatspi2.0-0t64 fonts-noto-cjk fonts-noto-color-emoji fonts-inter` (Inter sets Latin text; the CJK font would draw punctuation such as ’ full width), then `ldd chrome-headless-shell | grep 'not found'` should print nothing. Chrome starts for each card (about 0.6 s and 100 MB) and exits; nothing runs between cards. To upgrade it, unpack a newer build beside the old one and point `chrome` at it. X posts come from FxTwitter's public API, or from X's embed endpoint when FxTwitter fails; both depend on X tolerating unauthenticated reads, and a post neither returns gets no card (recorded as `twitter.card`, outcome error).
- The `bilibili` module also offers agents tools, in the chats on the chat module's `tools:bilibili` list. `bilibili_video` gives a video's title, uploader, date, length, description, counts, and parts, looked up as the cards look videos up, with no login. `bilibili_subtitles` gives a part's subtitles, one line each without times, the uploader's Chinese track before the one Bilibili generates; agents get it only with `yt_dlp` and `sessdata` set. Both take a video by its BV ID, its av number, or a link, share links included. The subtitles come through [yt-dlp](https://github.com/yt-dlp/yt-dlp), which this module runs rather than calling Bilibili's subtitle API itself: install its single-file build (`yt-dlp_linux`, no Python needed) anywhere the service user can run it and point `yt_dlp` at it; when subtitles start failing, update it first (`yt-dlp_linux -U`, or a newer release in its place). `sessdata` refers to a secret holding a Bilibili login: in a browser logged in to bilibili.com, the value of the `SESSDATA` cookie (developer tools, Application, Cookies). It lasts about half a year and ends sooner if that login is logged out (in the Bilibili app's list of logged-in devices); a subtitles call then tells the agent the login has stopped working, and someone sets a fresh value. yt-dlp gets the login in a cookie file only the service user can read, removed when it exits, and runs with `--ignore-config --no-cache-dir`; one run takes about 2 s and is stopped after a minute. Most videos without an uploader's track get one Bilibili generates, not all (5 of 8 popular videos in November 2026). `max_subtitle_chars` (default 15000, about an hour of Chinese speech) caps what one call gives: a tool's result stays in the thread and is sent again with each turn after. Each call is recorded as the chat module's `chat.tool`. There is no search tool: yt-dlp's Bilibili search is refused by Bilibili (HTTP 412) as of November 2026.
- The `decision` module (Decisions in the panel) answers other modules' yes/no questions with TypeSafe Jev; it handles no messages itself. Its settings are under `jev`: `api_key` (a reference such as `${OTOGI_TYPESAFE_API_KEY}`), and optionally `base_url` (default `https://api.typesafe.ai/v1/systemone`), `model` (default `jev-latest`, which follows TypeSafe's upgrades; thresholds tuned against one version stay put when it is named, such as `jev-1.14.0`), and `timeout` (default 5s; a request is not retried). Each request is a `decision.completed` or `decision.failed` record. Live test against TypeSafe: `OTOGI_TYPESAFE_API_KEY=... go test -run Live -v ./modules/decision`.
- Wherever a chat agent's model is shown the chat (the recent messages, quotes, a batch's messages, judgments), a line the account sent for an agent reads as that agent's: its `label`, or its name, with "(this account)", without the label its reply showed first. Left in, the label was copied: replaying an Eku group, 8 and 25 of 27 replies began with the agent's name, and none without it. Agents sharing the account stay apart by their names; the account's other messages, such as cards, read as the account's name with "(this account)". The transcript keeps lines as sent, so this applies to lines kept before too, except that a line sent under an earlier `label`, or before `plain_text` was turned on or off, keeps that label.
- A chat agent's `plain_text` (off by default) has it reply in plain text, for an agent that talks like a member of the chat: the system prompt asks for plain text instead of Markdown, and what the model writes is sent as it is, trimmed, not read as Markdown, so asterisks and emoticons such as `(*/ω＼*)` stay as written. The label is not bold, and a grounded reply's sources are written as `Sources: title (address)`. With `sources` off (on by default), a reply ends with what the model wrote, without that line; `chat.reply` still records the pages. With nothing formatted, a reply on QQ is an ordinary text message, as members' are, and on Telegram one without entities. One limit: a reply streamed in a QQ private chat is still shown by QQ as Markdown, so `*…*` there may show in italics and an emoticon lose its asterisks; group chats are not affected.
- A chat agent's `own_format` (off by default) leaves how it formats a reply to its own `system`: the system prompt asks neither for Markdown nor, with `plain_text`, for plain text. It concerns the prompt only; whether what the model writes is read as Markdown is `plain_text`'s. Eku is `own_format` with `plain_text` off, as on dsh, where every reply was sent to QQ as Markdown and her persona alone kept her to plain text, code aside: a code block shows as code, and an emoticon's asterisks may be read as formatting.
- A chat agent's `quote` says whether its reply quotes the message it answers (the last of a batch): `always`, the default; `never`, as Eku never did on dsh; or `when_interrupted`, only when the transcript has a line after that message and before the reply starts, anyone's, the agent's own earlier reply or another module's card included, since then the chat no longer shows what the reply answers. It is decided as the reply starts, from the transcript, whatever the agent's `context`: lines sent while the reply is written do not count, so a reply that took a while may go out unquoted with others' messages in between; a streamed reply's first message goes out at the start, so the decision cannot wait. Telegram gives times in seconds: a line in the same second as the message answered counts as before it. A sticker after the reply quotes as the reply does, and a reply sent as two messages quotes in both or neither. Quoting or not does not change threads: a reply to the agent's message carries on its thread either way. QQ never gave the agent's own lines in the transcript what they replied to; on Telegram, which does, an agent that does not quote loses that from its lines, and judgments no longer see whom it answered.
- A chat agent's `failure_notes` says where a reply says how it failed or that it has no answer: "Sorry, I couldn't reply: …" and "(Cut short: …)" after an error, "I can't answer that (…)" and "(The rest was blocked: …)" when the provider blocked it, and "I couldn't come up with an answer (…)" and "I have nothing to add." when the model wrote nothing. `everywhere`, the default, sends them in every chat; `direct_chats` only in direct chats, as Eku on dsh, so that in groups and channels a failed reply sends what the model wrote and nothing after it, or nothing at all. A reply cut off by its length limit still ends with "…", which is part of the text. `chat.reply` records why either way: an error as its `error`, a block or an empty answer as `finish` and `reason`. A batch that gets no message and no error, because the model wrote nothing and no note says so, is not kept in a thread, as with `stay_silent`, and its `chat.reply` is skipped with `skipped: no_answer`.
- A chat agent's `notes` end each turn it answers with a note, by what started the turn: `mention`, `reply`, `keyword` (private chats included), `decision`, `follow`, and `chime`, the triggers `chat.reply` records. A note goes in that request only, not into the thread, as Eku's per-turn notes did: on Eku, "keep it short" left only in the system prompt doubled the length of replies. A follow-up and a chime have built-in notes by default (nobody named you, or you chose to join in; keep it short), which the panel shows and setting `follow` or `chime` replaces; other turns have none. Removing a built-in note takes setting it to an empty string through the management API: the panel leaves an emptied field unset, which is the default. A chat agent's `silent` (off by default) gives it a tool on every turn, `stay_silent`, that ends the reply sending nothing; words written before it still go out, and a sticker picked with it goes out alone. When to use it is for the prompt and the notes to say: nothing in the code rules it out on a turn, so a note advising against it where the agent was called is advice, and with `silent` on and no note about it the model decides on every turn, when mentioned or named too. A turn with nothing sent is recorded as `skipped: silent` with its `trigger`, which shows how often each kind of turn went unanswered; it is not kept in the thread, and the messages that came meanwhile are answered without asking whether it did for them.
- A chat agent's `judge` settings have the decision service judge its group messages; they need the `decision` module on, and saving them while it is off is refused. `judge.wake` (`threshold`, default 0.7) answers a group message no reply or mention caught, and that does not reply to another module's message such as a card, when the judgment says it is addressed to the agent; when several agents pass, the surest answers. A message starting with the agent's keyword is judged too, in a group, since starting with a name is not always talking to it; with a mention, the keyword still picks the agent, and when the judgment fails (the decision service times out, is rate limited, or errs), the keyword triggers the agent as it would without `judge.wake`. Private chats and agents without `judge.wake` keep the keyword trigger. `judge.rules` says what else counts, or does not, as talking to the agent, such as its name also being a product people discuss. With it on, every such message in the agent's allowlisted groups is one decision request: about 2,200 input tokens with Jev (the last 10 messages, each but the judged one cut to 150 characters), about $0.09 per 1,000 group messages at $0.042 per million input tokens, and one `decision.completed` record holding those messages. To pick a threshold, replay a real chat kept outside the repository, one JSON object per line (`from`, `text`, and optionally `agent` for the agent's own messages and `addressed` true or false): `OTOGI_CHAT_REPLAY=chat.jsonl OTOGI_CHAT_REPLAY_AGENT=<name> OTOGI_TYPESAFE_API_KEY=... go test -run Replay -v ./modules/chat` prints each message's score and how many messages each threshold wakes.
- A chat agent's `judge.wait` (`min`, default 2s; `max`, default 20s, at most half of the agent's `timeout`, since the reply must fit in what is left) has it wait in groups for the sender to finish before answering. The message that calls it and those that call it while it waits are one batch, answered in one reply to the last; when it holds several, the model is told under "Answer:" who said what, and what others said before the first stays in the recent chat. The recent chat runs up to when the reply starts: what was said after the last message to answer, the agent's own reply to an earlier batch among it, comes under "Sent after the message to answer:", before the messages to answer, which still end the turn. So does what a group says while an agent waits to chime in. A sender judged finished is answered `min` after their message; one not finished, up to one and a half of their rhythms later (the median gap between lines they send in a row, at least 3s, leaving out gaps in which an agent started a reply); never later than `max` after the batch's first message. Messages calling the agent that arrive while it replies wait for that reply, and are answered after it unless a judgment says it already did for them (0.7, fixed in the code: Eku's live value, to tune by the records), then logged as `chat.reply` with `skipped: covered`. Private chats do not wait. It costs one more question on each message judged for `judge.wake`, a request of its own for a message a keyword, reply, or mention calls the agent with, and one request before answering messages that came during a reply; messages arriving within the shortest `min` of each other in a group are judged in one request, so in a group where any agent waits, every message to be judged waits up to that long before its request, and the agents there that do not wait answer that much later too. Waiting holds workers (the process section's `workers`, default 32, shared by every module): a batch being waited for holds one for up to `max`, at most one per agent and group, so at most the agents with `judge.wait` times their groups; and each message being judged in a group with a waiting agent holds one for `min` plus a decision request while its request gathers others. When these come near `workers`, other modules' deliveries queue behind them, not dropped; raise `workers` for many such groups.
- The `media` module (Media descriptions in the panel) describes the images, animations, and videos of people's new messages in the chats on its `describe` list, once per content (QQ names pictures by their MD5; other media is fetched and known by its SHA-256), so chat agents can read what they show. Its `steps` are the models it tries in order (`provider`, `model`, optionally `thinking`; `minimal` is enough): an error, a block, an answer out of format, or media the model did not get moves to the next. Configure at least two, since Gemini's free tier often answers 503 when busy, and on the free tier each model has its own daily limit. Use only providers whose model sees images and video: `deepseek-v4-pro` drops an image without saying so and answers as if it had seen one, so descriptions would be made up. `language` (default English) is what descriptions are written in; text on pictures and what videos say are copied as they are. Animations go to the model as six frames; media over `max_media_mb` (default 25 MiB) is neither described nor examined, which bounds memory rather than any API: a piece is held about 2.3 times over while it is described, and several can be described at once (QQ videos run about 1.7 MB per 21 seconds, so 25 MiB is some four minutes; Eku described videos of up to 50 MB). It is not the chat module's own `max_media_mb` (default 20), the largest picture or file an agent is shown itself. Nor is a GIF that would take more than 80 MiB to decode, counted from its frame sizes before decoding: frames of one color compress about a thousandfold, so a small file can decode to gigabytes, and the message would be dispatched again after the process died. A GIF whose blocks do not read exactly as Go's image/gif reads them is not described either, since its count could not be trusted. eku's largest of 61 GIFs took 67 MiB. A description is kept in the module's database until the media goes unseen for 30 days. Each one is a `media.described` record with its token usage; each failed step is a `media.failed` record, and media left alone a `media.skipped` one. Live test against Gemini: `OTOGI_GEMINI_API_KEY=... go test -run Live -v ./modules/media`.
- Operators keep stickers, the pictures agents may send, with the media module's `/sticker` command: `/sticker add [note]` replying to a picture, or sent with one (in a private chat with the bot, that is how a picture is imported); `/sticker list`; `/sticker note <n> [note]`, an empty note clearing it; `/sticker remove <n>`. Only `operators` may use it, in chats on the `describe` list and in private chats. A reply finds a picture for two hours after it was sent, and on QQ a picture's link stops working after about an hour: send it again and add it at once. Only PNG, JPEG, and GIF pictures are kept, told by their content: Telegram's GIFs are MP4 files and are refused, and WebP is not kept yet. A sticker is at most 9 MiB, since QQ refuses uploads over about 10 MB and its driver uploads in one request. There is no limit to how many are kept: they live in the module's database, and so in its backups, which grow with them; `/sticker list` shows 50 at most, the control panel all of them. A sticker keeps its own copy of its kind and summary, so pruning descriptions leaves it alone; one with neither a summary nor a note is listed with a mark and is left out of what agents get until it has a note. Numbers are not reused after a removal. Each action is a `media.sticker` record.
- The management panel does the same on the media module's page, in its Stickers card, and manages packs, which only it does. A row above the grid picks what it shows: all stickers, one pack's, or those in no pack, with New pack beside it and a filter by number or text; with a pack picked, Edit and Remove pack. For the sticker selected it shows its picture, note, description, packs (Add to pack, or take it out), the agents given it (directly, or through a pack, as `media.stickers` and `media.packs` name them), and a link to the `chat.reply` records that sent it. Upload, or drop pictures on the card, to keep them, with the same checks as `/sticker add`, into the pack picked if any: a picture kept already is then added to the pack. A refused one stays at the grid's end with the reason. A note is saved with Save or Ctrl+Enter, and notes not saved are kept while another sticker is selected, until the page is left. Removing a sticker or a pack does not take it out of agents' settings: the dialogs name the agents that still list it. Removing a pack keeps its stickers, or removes those in no other pack too, as you pick. The panel's actions are `media.sticker` and `media.sticker_pack` records by their caller, named as settings revisions name theirs, with no event. While the media module is not running, the card says so and offers nothing.
- A chat agent's `media` settings have it read those descriptions; they need the `media` module on, with the agent's chats on its `describe` list. In the agent's recent messages, quotes, and wake judgment, media then reads as described (`[sticker: …]`, a screenshot with up to `described_text` characters of its text, `[video 0:12: …]`) instead of `[photo]`. `described_text` is the chat module's (default 1000), and applies to each picture: a message of nine long screenshots reads up to nine times as much. Of Eku's 391 screenshots over some 15 days on dsh, 72% had their whole text in 300 characters and 97% in 1000, the longest 2,163. It applies to the message judged too (every other line of a judgment is cut to 150 characters): Jev takes 32k tokens for the state and any one question, and refuses a longer request (`400 max_tokens_exceeded`, a `decision.failed` record, and the message falls back to its keyword), which a judgment of about 2,200 tokens reaches only with some twenty long screenshots in one message; when one fails that way, look here first. With `as_text`, the current and the quoted message's media go to the model as descriptions instead of themselves, for a model that sees images poorly or not at all. A message waits for its own descriptions, all its media together, at most the chat module's `describe_wait.judge` (default 15s) from its arrival before it is judged, and at most `describe_wait.reply` (default 30s, or half of `timeout` when that is less; set, at most half of it) before an agent answers it with `as_text`, holding its worker meanwhile; a message described sooner waits no longer, and a quoted message's media is described already or never will be, so it is not waited for. The defaults are from Eku's 215 pictures over 48 hours on dsh (Gemini flash-lite, up to 3,000 characters of a picture's text): 90% of stickers, memes, and photos were described within about 10 seconds and of screenshots within 15, the slowest screenshot in 33; those times include Eku looking up a screenshot's original post, some 5 to 6 seconds (3.5 to 9.1 over 72 lookups in two days), which Otogi does not do, so its screenshots should be described a few seconds sooner, the defaults leaving room. A judgment waits less since a message nobody called for can do with what is described; someone who called an agent is waiting for an answer that saw the picture. `chat.media_skipped` records what was answered without its description. A batch waits for its senders from its first message, up to `judge.wait.max`, and for the descriptions of its last one, up to `describe_wait.reply`, so the two add up within `timeout`: set both to half of it, and the reply may have no time left. Media still undescribed reads as `[photo]`, and under `as_text` a `chat.media_skipped` record says why. A voice message the platform transcribed reads as its transcript, `[voice: Said: "…"]`, everywhere and for every agent, `media` settings or not: in the recent messages, quotes, and judgments cut to `described_text`, and in the message answered whole, given to the model instead of the audio and not waited on. QQ transcribes every voice message, whether or not its sender had the text shown; one without a transcript reads as `[voice]`. A sticker the platform sends by its name alone, a QQ market face from QQ's store, whose picture and ID the bot is not given, reads as `[sticker, picture not available: 被猪包围]` in the same places and for every agent, `media` settings or not; there is nothing to describe or look at. Lines kept before this showed the name alone, as `[被猪包围]`. QQ's built-in faces stay as their names, `[流泪]`.
- `media.stickers` lists, by the numbers `/sticker list` shows, the kept stickers an agent is given, and `media.packs` the sticker packs, by ID, whose stickers it is given; an agent with neither gets no stickers. Its list holds its stickers first, in its order, then its packs', in its order and each pack's by number, each sticker once and only those still kept: a sticker put in one of its packs is in it from the next reply on, and a pack removed is skipped. `media.max_stickers` (default 50, as many lines as about two thousand characters; Eku's list on dsh was 27) bounds it: past it, those first in it are shown, and `chat.reply` records how many were left out as `stickers_hidden`. In the panel's chat settings, the two are picked from the stickers kept: packs from a menu, with how many stickers each has; stickers from a grid, by pack, that Add stickers opens (a sheet on a narrow screen), where a press adds one at the end and another removes it. Each chosen one can be moved earlier or later, or removed; one no longer kept shows as such, to be removed. Under them a line says how many stickers the agent sees, and, past `media.max_stickers`, that it sees only the first. While the media module is not running, the two are the plain lists of numbers and IDs. The list follows the agent's system prompt, and the agent picks one with `send_sticker`, which ends its reply. It may also send a kept sticker not on its list when someone names its number, or when it was shown one as `[sticker N: …]`; the sticker follows the reply's words as a message of its own, at most one a reply, and the agent's recent messages read it as `[sticker: …]`. It needs the `media` module on. The list is about fifty characters a sticker, and comes before what changes with the chat and the minute, so it is cached with the persona: a reply pays for it in full only after it changed. How often an agent sends one is up to its prompt: say when it may. A kept sticker that anyone posts in a chat on the media module's `describe` list is known by its content, on QQ by the MD5 its file is named by: no model is asked, and for every agent with `media` it reads in the recent messages, quotes, and judgments as `[sticker N: …]`, with its note, else the summary it was kept with, so a note says what the picture means to the agents, and applies at once. A sticker with neither is described like any picture until it has a note. Verified on QQ only so far: whether a GIF sent on Telegram shows as an animation is for a Telegram bot to confirm (EXO-22).
- A chat agent's `media.examine` gives it `examine_media`, to look again at a piece of media for what its description leaves out: what exactly something is, a detail, a size, small text. The descriptions it is shown, in the recent messages, the messages it answers, and what they quote, then show their media's ID, the first six hex digits of the digest the media module knows it by (`[photo #2ce7ad: …]`, `[video 0:12 #9f03c1: …]`); a kept sticker keeps its number (`[sticker 3: …]`). Judgments, the memory, and other agents are shown no IDs. The agent names a piece of media by its ID, or a kept sticker as `sticker 3`, with a question, and gets back what the media module's `steps` answer from the media itself, tried in order as for describing; the tool does not end the reply, and its calls count against `max_tool_rounds`. The media is looked for among what the reply was shown, the thread's earlier turns included, the latest when two share an ID (in a chat with some 600 pictures, about one chance in a hundred). Its original is the media module's when the module keeps it (`pictures`, below), else fetched again by its platform link, which fails once the link expired: QQ's do in about an hour, and how long Telegram's last is unverified. `examine.timeout` (default 1m) bounds one look, fetching and every model tried: on Eku, Gemini Flash-Lite took 5.5 seconds at the median to describe a picture, 26 at the 99th percentile, and 33 at most, and its two looks took 9.7 and 23.6 seconds. A look that cannot be made, a link expired, past its time, or with every model failing, tells the agent so, to answer from the description. Each look is one more request to a describing model, with the whole picture or video again (a video's tokens grow with its length), and a `media.examined` record; `chat.tool` records the call, with its error, which counts the looks a kept original would have saved. On Eku, the agent looked 16 times in 19 days, about once every 80 replies; of the 9 looks matched to their pictures, 6 came within a minute of the picture.
- A chat agent's `media.resend` gives it `resend_media`, to send a picture or animation of the chat again when someone asks for it: on dsh, Eku did so 5 times in 20 days. Its descriptions then show IDs, as with `media.examine` (either one shows them), and the agent names the picture by its ID; it is looked for as `examine_media` looks, so only what the reply was shown, in its own chat, can be sent. It follows the reply's words as a message of its own, quoting as the reply does, and ends the reply as `send_sticker` does: one picture or sticker a reply, a second answered as not sent. The picture is the media module's copy when it keeps one (`pictures`, below), else fetched again by its platform link, which fails once the link expired (on QQ, in about an hour); the agent is then told so, and says it in words. Videos, whose originals are not kept, and kept stickers, which `send_sticker` sends, are not resent. The platform's limits on what it takes are the driver's: a picture it refuses makes the reply an error, with the words sent. `chat.reply` records `resent`, `chat.tool` the call. The bot does not describe what it sends, and QQ gives the bot's own picture back as the text `[image]`, with no attachment: the agent's line in the recent messages then reads `[image]`, not what the picture shows.
- The media module's `pictures` (unset by default) has it keep the pictures and animations it describes, in its database and so in its backups, for `examine_media` after their links expired: one copy per content, looked at only from the chats it was seen in. Videos are never kept. A picture described already, such as a sticker sent again, is fetched once more to be kept, and not described again: on QQ, which names pictures by their MD5, it is otherwise not fetched. `pictures.max_mb` (default 512) bounds them in all, pruned hourly back under it, the longest unseen first, so between prunings they can go somewhat past it; and a picture goes with its description, 30 days unseen. How long one is kept depends on how many come: Eku's groups sent about 100 pictures a day, 60 to 86 MB, so 512 keeps six to eight days of them, and a quieter chat's longer. It keeps what people sent; unset, agents still look at a picture while its link works. Unsetting it deletes the pictures kept at the next hourly pruning, for good.
- A chat agent's `judge.follow` (`threshold`, default 0.6) keeps up an exchange it is in. While the agent has a line in the group's last 10 messages, with no gap of more than 30 minutes since, each message there that no trigger caught is also asked, from the agent's point of view, whether it carries on that exchange and wants an answer: a topic that drifted still counts; a reaction that needs no reply (a laugh, agreement, thanks, a sticker that only shows a feeling) does not, nor does talking to someone else. Past the threshold the agent answers as if called, told in the turn that nobody named it and to keep it short, and the reply is logged with `trigger: follow`; a message addressed to the agent wakes it by `judge.wake` instead. So that the agent does not keep following up on its own, the threshold rises with its share of the conversation (the messages since the last 30 minutes of quiet): its follow-ups over the messages of the middle member among those with two or more, replies it was called for not counted. Past 1.3 it rises by 0.1 per time more, up to 0.8; a threshold set above 0.8 stays. These numbers are in the code: 1.3 is where Eku's owner set it to start, while 0.1 and 0.8 have no replay behind them, so a follow-up the share alone held back is logged as `chat.held`, to tune them by. The sender's `threshold_factor` multiplies the threshold as it does `judge.wake`'s. With `judge.wait`, a follow-up waits for its sender as a message calling the agent does, and someone who sends runs of lines is waited for at least two of their rhythms, since each of their lines may look finished. It costs one more question, about 100 input tokens, on each message judged while the agent is in an exchange, a request of their own for those messages when the agent has no `judge.wake`, and the replies. To check it against a real chat, the replay file's lines also take `at`, when the message was sent in Unix milliseconds, and `kind: "chime"` on the agent's own lines it said unasked; `go test -run ReplayFollow`, with the same variables, prints each candidate's score and the agent's share, and how many each base threshold would answer and hold back.
- A chat agent's `judge.chime` (`threshold`, default 0.55) has it speak up unasked in a group conversation it is not in. While it has no line in the group's last 10 messages, and neither gathers a batch nor replies there, each group message is also asked, from the agent's point of view, whether it would like to chime in: a question nobody answered, a topic it could add to or joke about, or people talking about it counts; a short reaction, private talk between others, an argument, politics, or a video it cannot see does not. The threshold rises with the agent's share of the conversation as `judge.follow`'s does, its chimes and follow-ups both counting, and a chime the share alone held back is logged as `chat.held`. It needs `judge.wait`, and saving it without is refused. Past the threshold the agent does not speak at once: the message opens a batch and waits in its own `Handle` for the chat to pause, a silence of 2 × (1 + 2 × (1 − score)) of the sender's rhythms (2 to 3.8 past 0.55; a sender with no rhythm of their own takes the group's, else 10 seconds), at most 2 minutes after the message and at most half of the agent's `timeout`. Each message meanwhile that does not call the agent asks whether it still means to speak up (`judge.chime.still`, default 0.5, the default of Eku's code; Eku runs at 0.4): if so, the pause is counted again from that message, by its sender's rhythm; if not, or once the message it meant to add to has left the last 10, it gives up, logged as `chat.reply` with `skipped: still`. A message calling it meanwhile joins the batch, which from then is one it was called for, waiting for that sender as `judge.wait` does; it answers both, and is not told it chimed in. When it speaks up, the turn tells it that nobody asked and to keep it short, and the reply is logged with `trigger: chime`. 0.55 and the pause are Eku's: in a replay of three of its group chats, thresholds from 0.5 to 0.65 made 20 to 22 chimes, where Eku made 14, and of 61 waits in Eku's live logs about 52 ended in speaking and 9 in giving up. It costs one more question, about 100 input tokens, on each group message while the agent is out of the conversation, the question whether it still means to on each message during a wait, and the replies; a wait holds one of the process's `workers` for up to 2 minutes, at most one per agent and group. `go test -run ReplayChime`, with the replay variables, prints each candidate's score and share, and how many chimes each base threshold would make. To see the agent as it would act live, waiting, following up, and speaking up or giving up at the times the chat's messages were sent, `go test -run ReplayTimed -timeout 0` replays a file whose lines all have `at` to an agent with `judge.wake`, `wait`, `follow`, and `chime` on at their defaults, with a model's key too (`OTOGI_DEEPSEEK_API_KEY` or `OTOGI_GEMINI_API_KEY`) and the agent's prompt in the file `OTOGI_CHAT_REPLAY_SYSTEM` names; lines with `history: true` are the transcript before it starts, and the agent's own lines after them are left out, as the replayed agent speaks for itself. It prints each message and reply as they come and then counts them, and runs on virtual time, so a half-hour chat takes as long as its requests; `OTOGI_CHAT_REPLAY_REALTIME=1` runs it on the real clock instead.
- A chat agent's `judge.brief` (`lookup`, default 0.7) asks, before each of its replies, in groups and private chats alike, whether it should look things up online before answering what it is about to answer. Past `lookup`, the turn it answers ends with a note telling it to; the note goes with that request only, not into the thread, so later replies do not see it. It needs `web_search` or `url_context` in the agent's `tools`, and saving it without either is refused, since the note would send the agent to a search it cannot make. The question and 0.7 are Eku's, live since 2026-11-18: of twenty real group rounds, the ten that needed a search scored over 0.75, and the small talk under 0.13. A judgment that fails leaves the reply as it would be without `judge.brief`, with no note. It costs one decision request before each reply, with the recent chat, about 2,000 input tokens at Eku's rate; with `judge.wait`, the question whether a reply already did for the messages that came during it is asked in that same request.
- A chat agent's `judge.stale` (`threshold`, default 0.8) checks a group reply before its first message goes out, when someone else spoke after the agent started it: one decision request asks whether whoever asked took the question back ("never mind", "got it myself"), and whether someone else already answered it. Either past `threshold`, and nothing goes out, the sticker neither, and the turn is not kept; a reply held back where the model first speaks before its tools ends there, the tools not run. The messages that came meanwhile are handled as ever, and those that call the agent are answered as the next batch, without asking whether the reply did for them, since none went out. It does not ask whether they made the reply wrong: a correction or an addition leaves the question standing, and the addition may not call the agent, so holding the reply back would leave the asker without an answer. "Started" is as for the recent chat (the later of the reply's start and the messages it answers); the account's own messages are not someone else speaking, but other bots' are, the transcript not keeping who is a bot: a card another bot posts meanwhile is one more request. A judgment that fails sends the reply. The agent does not stream in groups, so nothing shows before the check: on Telegram its group replies appear when written. The two questions are two of Eku's three, and 0.8 its threshold: over six days it asked 32 times, about 1,300 input tokens each, 0.7% of its decision input; over the two days with logs none was held back, and at most two over 19 days. The cost is that request, a reply waiting for it (up to the decision service's timeout) when the chat spoke meanwhile, and a reply wrongly held back, which nobody is told of: check what `skipped: stale` holds back.
- The chat module's `people` list tells agents more about some people than the name the platform gives them; it is shared by every agent. Each entry's `user` is the platform (`qq` or `telegram`), a colon, and the person's sender ID: a chat's page in the control panel lists the people seen there under People, each with that ID below their name (`user:7C2E…`), so a person on QQ is `qq:user:7C2E…`. Set up beside a person there adds them to `people` on the chat module's page, the ID filled in, as an edit to apply with the others, or opens their entry when they have one; the list shows the entries people have, with their `name`. It offers every list in the settings that names people, `operators` among them. On QQ a person's ID is the same in every group and private chat, so one entry covers them everywhere; the same person on Telegram is another entry. Saving a `user` that is not platform:ID, or one listed twice, is refused. `name` is what agents call them: wherever a model is told who sent a message, judgments included, it reads `name (the platform's name)`, since people mention them by the name the platform shows; the transcript keeps the platform's names, so a change applies at once to the recent messages and judgments, which are read from it each time, while a thread's earlier turns keep the names they were sent with. `note` says who they are: the notes of the people in a request, its sender, whom they quote, and the recent messages shown, lead it under "About people here", in that request only. `threshold_factor` (0.1 to 10, default 1) multiplies the judgment thresholds of their messages: at 0.9, a 0.7 threshold wakes an agent at 0.63; a factor that takes an agent's thresholds past 1 leaves their messages unjudged for it (each one gets a `chat.unjudged` record saying so), so judgments never wake it for them, while mentions and replies still do.
- Chat agents tell the bot's `operators` (General) from the names people take: wherever a model is told who said what (the recent chat, judgments, a batch, a quote, the message it answers, notes on people), an operator's name is followed by `⟦operator⟧`, added by their account, and the system prompt says so while there are operators. The mark, or half of it (`⟦`, `⟧`), is taken out of every name a platform gives, so someone who takes an operator's name, mark included, reads as someone else with that name. A change to `operators` applies from the next message; a thread's turns keep the names they were sent with. What it does not cover: people on the `people` list who are not operators, whose names can still be taken; a mark typed in a message's text, or in a chat's title or description; and brackets that only look like it, such as `〚operator〛`. Anything people wrote that goes into the system prompt, such as long-term memory, is to have the mark taken out first (`withoutOperatorMark`), since that is where the mark is explained. Judgments see the mark too; their thresholds were tuned without it.
- A group's owner and its admins are marked the same way, `⟦group owner⟧` or `⟦group admin⟧` after the name and before `⟦operator⟧`, by the standing the platform gives with each message: QQ gives it in groups (`member_role`); Telegram gives none, so nobody is marked there. The transcript keeps each message's standing, so a message reads with the standing it was sent with, and messages from before the transcript kept it are not marked. The system prompt explains these marks only when a turn shows one. Names lose them as they lose the operator mark (`withoutOperatorMark` takes out every `⟦` and `⟧`), and the same limits apply: a mark typed in a message's text, and brackets that only look like it. Agents are told who holds the standing, not how to treat them.
- A Telegram account's `upload_threads` (default 8) is how many parts of a file it uploads at once. Each part waits for Telegram's answer, so one at a time is slow far from the account's data center (about 450 KB/s from Los Angeles).
- `otogi validate` checks a config file without starting drivers or touching data. It checks the file only: the settings edited in the panel were checked when they were saved.
- The control panel is served by the bot at every path outside `/api/`, from the build embedded in the binary (`web/`), when `management.public_url` names where it is reached. Put a TLS reverse proxy in front that passes the whole site to `management.addr`, keeping `Host` and setting `X-Forwarded-For` (nginx: `proxy_pass http://127.0.0.1:8383; proxy_set_header Host $host; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`). Sign-in goes through an OpenID Connect provider: register a confidential client there with the redirect URI `<public_url>/api/auth/callback` and the post-logout redirect URI `<public_url>/sign-in`, then set `management.oidc` (`issuer`, `client_id`, `client_secret` as a `${VAR}` reference, and `allow`, the provider usernames that may sign in).
- What a change needs depends on where the setting is. The general settings, the language model providers, the modules, the allowlists, and the secrets apply when they are saved, without a restart. The platform accounts and the process settings are saved in the panel and apply at the next start, which `POST /api/restart` asks for. What is in `otogi.yaml` (the data directory, the management API and sign-in) is read at startup: changing it means editing the file on the server and restarting.

## Data directory

```text
<data>/
  eventlog.sqlite                 # event log, and the directory of chats seen
  panel.key                       # the key that seals the control panel's session cookies
  modules.sqlite                  # module key/value state and timers, settings, secrets set in the panel, model lists fetched
  modules/<id>.sqlite             # a module's private database, if it uses one
  telegram/<account>/session.json # gotd session (login)
  telegram/<account>/state.sqlite # inbox, update state, send records
```

Each Telegram account has its own session and database. The database records which account it belongs to, and startup refuses a database that belongs to another account, which prevents mixing up accounts.

## SQLite

- WAL mode, `synchronous=NORMAL`, a busy timeout, and foreign keys on, all set when opened.
- Each owning component embeds its migrations and applies them forward-only at startup. A database newer than the binary is refused.
- Never copy a live database file; use the backup methods below.

## Backup and restore

**Backup**
- Bot stopped: copy the data directory.
- Bot running: for each database, run `sqlite3 <db> ".backup <dest>"` (or `VACUUM INTO`), and copy the session files.

**Restore**
1. Stop the bot.
2. Put the files back in the data directory.
3. Start the bot.

Telegram fetches any updates newer than the restored state. A backup holds what the data directory holds: the session files, the messages in the event log, and, in `modules.sqlite`, the secrets set in the control panel as given. Keep it as the data directory is kept, readable only by the service user. Encryption and off-host storage of backups are up to the operator.

## Upgrades

1. Back up.
2. Replace the binary and restart. Migrations run at startup.
3. To roll back, restore the backup taken before the upgrade if the new binary migrated a schema; otherwise just swap the binary back.

Upgrading gotd also changes the Telegram API layer. Follow the gotd upgrade steps in the [Telegram runbook](runbooks/telegram-mtproto.md#gotd-upgrade).

## Signals and exit codes

- SIGINT or SIGTERM starts graceful shutdown (see `runtime.md`); a second signal forces exit.
- Exit 0 means a clean stop: a signal, or `POST /api/shutdown`. The supervisor leaves the process stopped.
- Exit 75 means a restart was requested with `POST /api/restart`: the process stopped as cleanly as for exit 0, and is to be started again. The supervisor's rule of restarting on a non-zero exit does that; the panel's restart button relies on it. The `process.state` records of that stop carry `restart_requested_by`. If the process does not come back, start it on the server.
- Any other non-zero code means a startup failure, a component failure, or a forced stop, and the reason is printed on stderr.

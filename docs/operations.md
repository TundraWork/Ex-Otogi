# Operations

## Deployment

One `otogi` process plus its data directory on one host, run under a supervisor (systemd, Docker, or similar) that restarts it on non-zero exit. The data directory is on local disk; SQLite WAL does not work over network filesystems.

## Configuration

- One YAML file (`otogi.yaml`; see [`otogi.example.yaml`](../otogi.example.yaml)) holds what decides whether the panel can be reached at all: the data directory, and the management API with the panel's sign-in. `GET /api/system/startup` shows these as the running process read them, with the file's path and each secret only as set or not. The other settings are edited in the control panel while the bot runs and kept in `modules.sqlite`: the general settings, the language model providers, the platform accounts, and the process settings (below), and the modules.
- Settings outside modules that are edited in the panel are grouped in sections, each kept as revisions exactly as a module's settings are: `GET /api/system` lists them, `GET /api/system/{section}/settings` returns the current revision and the JSON Schema, `PUT` saves a new revision against the `ETag` it replaces, and any earlier revision can be restored (see `docs/management-plane.md`). A saved revision of `general` or `llm` applies at once, without a restart. One of `accounts` or `process` is validated and stored, and the process runs with it from its next start: `GET /api/system` gives each section's `applies` (`now` or `restart`) and `running`, the revision the process runs with, so a restart is pending while `revision` is newer. `POST /api/restart` restarts (see [Signals and exit codes](#signals-and-exit-codes)). Every saved revision is recorded as `system.reconfigured`. A section never saved runs on its defaults.
- The `general` section (Settings, General in the panel): `operators`, the platform-qualified actor IDs (`telegram:user:123`, as `/whoami` prints them) allowed to use operator commands, which are `/status`, `/todou link`, and `/sticker` (the bot's own messages never are: the account is the bot's); `command_prefixes` (default `["/"]`; an empty list turns commands off); `eventlog_retention` (default `720h`), which the hourly prune reads each time; and `log_level` (`debug`, `info`, `warn`, `error`; default `info`). Where modules answer is chosen in the control panel.
- The `llm` section (Settings, Language models in the panel): `gemini` configures the Gemini provider with `api_key`, a reference to a secret such as `${OTOGI_GEMINI_API_KEY}`, and an optional `base_url`, the API endpoint with or without its version (default `https://generativelanguage.googleapis.com/v1beta`; a proxy or gateway that speaks the Gemini Interactions API works too). Modules name the provider and pin their own model. Saving builds every provider from the new settings and rebuilds the running modules that were built with a provider, so their next request uses the new address and key; if a provider or one of those modules does not build, nothing changes and nothing is saved. Replacing a secret a provider refers to does the same. Live tests against the API: `OTOGI_GEMINI_API_KEY=... go test -run Live -v ./internal/adapter/gemini`.
- In the `llm` section, `openai.<name>` configures a service that speaks the OpenAI Chat Completions API, such as DeepSeek, under the provider name agents use: `base_url`, the API's base without `/chat/completions` (`https://api.deepseek.com`, `https://api.openai.com/v1`), and `api_key`, a reference to a secret such as `${OTOGI_DEEPSEEK_API_KEY}`. Names are lowercase letters, digits, `-` and `_`, and not `gemini`. On DeepSeek, an agent's `web_search` and `url_context` are DeepSeek's server tools. Images go to the model as they are: pick a model that sees them. A DeepSeek model that does not (`deepseek-v4-pro`, checked 2026-11-23) answers without error but drops them, and may make up what they showed; another service may refuse every request whose history holds an image. Live tests against DeepSeek: `OTOGI_DEEPSEEK_API_KEY=... go test -run Live -v ./internal/adapter/openai`.
- The `accounts` section (Settings, Accounts): `telegram`, the Telegram user accounts, each with `account` (the name it has in events and in the paths of its files), `app_id`, `app_hash` (a reference to a secret, such as `${OTOGI_TELEGRAM_APP_HASH}`), and optionally `session`, `database`, and `upload_threads` (default 8); and `qq`, the QQ bots, each with `account`, `app_id`, `app_secret` (a reference to a secret), and optionally `database`. Saving checks the shape and that each secret is set; whether the platform accepts the credentials shows only when the driver starts. A driver that does not start stops the process, so after a restart with a wrong credential the bot is down and the panel with it: see [The bot does not start after a settings change](runbooks/control-panel.md#the-bot-does-not-start-after-a-settings-change). A new Telegram account is logged in on the server (`otogi login ACCOUNT`) after it is saved and before the restart. Replacing a secret an account refers to restarts nothing: it too is read at the next start.
- The `process` section (Settings, Process): `workers` (default 32), how many deliveries to modules run at once; `max_in_flight` (default 1024), how many events may be admitted and not finished before the drivers wait; `handler_timeout` (default `10m`), the bound on one delivery for a module that sets none; `log_format` (`json` or `text`; default `json`); and `shutdown_timeout` (default `30s`). `GET /api/status` shows the workers, `max_in_flight`, and `handler_timeout_ms` the process runs with.
- `${VAR}` in any value of the file is read from the environment, which is how secrets such as the management token stay out of the file. An unset variable is an error. Use block style for such values; in flow style (`{...}`) quote them.
- `-config PATH` selects the file (default `otogi.yaml`); the first argument selects the command: `run` (default), `validate`, `login ACCOUNT`, `settings revert ID`, or `smoke`. `validate` checks the file only; the settings in the panel were checked when they were saved.
- The whole config file is validated at startup before anything starts. Errors name the field or the line. Unknown fields are errors, so typos surface.
- The keys that moved to the panel (`operators`, `commands.prefixes`, `eventlog.retention`, `log.level`, `llm`, `telegram`, `qq`, `kernel.*`, `log.format`, and `shutdown_timeout`) are still accepted in the file, for upgrades. On the first start that finds a section without a revision, the file's keys for it are saved as its first revision, by `otogi.yaml`: an API key written as `${NAME}` is kept as that reference and stays in the environment, and one spelt out in the file is moved to a secret (`OTOGI_LLM_<PROVIDER>_API_KEY`, `OTOGI_TELEGRAM_<ACCOUNT>_APP_HASH`, `OTOGI_QQ_<ACCOUNT>_APP_SECRET`) that the settings refer to. An account's `app_id` taken from the environment is saved as its value. An account's `session` and `database` are saved only where the file sets them: unset, they stay under the data directory. From then on the file's keys for that section do not apply: each start logs one warning naming them, and they can be removed. Remove them before removing the variables they name from `otogi.env`, since a `${VAR}` left in the file must still be set. A new install has none of these keys and starts on the defaults: no operators, no language model providers, and no platform accounts, with the panel reachable to add them. `otogi login ACCOUNT` reads the accounts set in the panel, and before the first start after an upgrade, the file's.
- Modules are not in the config file either. Which modules run and each module's settings are runtime data in `modules.sqlite`, changed through the management API: `GET /api/modules/{module}/settings` returns the current revision and the settings' JSON Schema, whose `doc` texts describe every field; `PUT` saves a new revision, which is applied at once (see `docs/management-plane.md`). A secret, such as a todou token, is never part of the settings: they hold a reference to it, `${NAME}`, resolved when the module is built. Each saved revision is recorded as `module.reconfigured`, and any earlier one can be restored.
- QQ sends names only now and then: a group member's nickname with some messages, none in private chats, and no group names. The QQ driver keeps every name a message shows. QQ's group info and member list APIs (group name, description, member count, member nicknames) are open only to whitelisted bots: the driver asks once a day per group, and when QQ refuses (code 11253), it records that once as `driver.lookup` and stops asking until restart. Name a QQ group or private chat in the panel to give it a name everywhere, agents included.
- Secrets that settings refer to, a module's or a language model provider's, are set in the control panel or through the management API (`PUT /api/secrets/{name}`), which stores them in `modules.sqlite` in the data directory, or are left in environment variables (`otogi.env`). A reference `${NAME}` takes the secret of that name set in the panel, or else the environment variable of that name; neither is an error naming the secret. Setting, replacing, or deleting one rebuilds the running modules that refer to it at once, and the language model providers that refer to it with the running modules that use a provider, and is refused, with nothing stored, if one of them does not build. Each change is recorded as `secret.changed`, without the value. Existing deployments need do nothing: a secret in `otogi.env` keeps working, and once one of the same name is set in the panel that line can be deleted. The `${VAR}` values in the config file (platform accounts, the management token, the OIDC client secret) are still read from the environment only.
- Allowlists say where modules answer: each chat agent, `bilibili`, `booth`, and `twitter` has one. The chat module also has one for each module whose tools agents may use (`tools:todou`, …): only the chats on it get that module's tools. They are runtime data in `modules.sqlite`, not config, changed in the control panel or through the management API; each change is recorded as `allowlist.changed`. So is each module's "ignore bots" switch (on unless turned off: messages from bot accounts do not reach the module), recorded as `bots.changed`.
- The `bilibili`, `booth`, and `twitter` modules answer Bilibili video links (`bilibili.com/video/…`, `b23.tv/…`), Booth items (`booth.pm/…/items/…` and shop domains such as `shop.booth.pm/items/…`), and X posts (`x.com/…/status/…`, `twitter.com`, and the fxtwitter/vxtwitter/fixupx mirrors) in the chats on their allowlists with a card image drawn by Chrome; `twitter` also takes a `timezone` (IANA name) for its times, `videos` (send a post's videos and GIFs after its card; default on) and `max_video_mb` (the largest one sent; default 50), and `translate` (`provider`, `model`, `thinking`): a language model then reads each post with text, and when it is not in Chinese the card also shows it translated into Simplified Chinese under the original (a quote's under the quote), marked with who translated it from what. The card then waits for the translation. How they censor pictures is the `safety` module's (Content safety in the panel): how far sensitive pictures are blurred (`blur`, default 9; 0 for none), whether a refused card goes out again under a sticker (`cover_refused`, default on), and the sticker (`sticker`, an image file on the server, default the built-in one; `sticker_opacity`, default 0.65; `sticker_size`, default 66 percent), and whether the videos of a post whose pictures are censored are sent anyway (`censored_videos`, default off). BOOTH and X cards need it on. How much each card module answers and shows is its settings: `max_videos` (bilibili), `max_items`, `max_options`, and `max_tags` (booth), and `max_posts`, `max_text`, and `max_quote_text` (twitter). All three need `chrome`, the path of a pinned [chrome-headless-shell](https://googlechromelabs.github.io/chrome-for-testing/) (`linux64` build, unzipped anywhere readable by the service user), its shared libraries, and fonts. On Ubuntu 24.04: `apt-get install --no-install-recommends libnspr4 libnss3 libatk1.0-0t64 libatk-bridge2.0-0t64 libxcomposite1 libxdamage1 libxfixes3 libxrandr2 libgbm1 libasound2t64 libatspi2.0-0t64 fonts-noto-cjk fonts-noto-color-emoji fonts-inter` (Inter sets Latin text; the CJK font would draw punctuation such as ’ full width), then `ldd chrome-headless-shell | grep 'not found'` should print nothing. Chrome starts for each card (about 0.6 s and 100 MB) and exits; nothing runs between cards. To upgrade it, unpack a newer build beside the old one and point `chrome` at it. X posts come from FxTwitter's public API, or from X's embed endpoint when FxTwitter fails; both depend on X tolerating unauthenticated reads, and a post neither returns gets no card (recorded as `twitter.card`, outcome error).
- The `decision` module (Decisions in the panel) answers other modules' yes/no questions with TypeSafe Jev; it handles no messages itself. Its settings are under `jev`: `api_key` (a reference such as `${OTOGI_TYPESAFE_API_KEY}`), and optionally `base_url` (default `https://api.typesafe.ai/v1/systemone`), `model` (default `jev-latest`, which follows TypeSafe's upgrades; thresholds tuned against one version stay put when it is named, such as `jev-1.14.0`), and `timeout` (default 5s; a request is not retried). Each request is a `decision.completed` or `decision.failed` record. Live test against TypeSafe: `OTOGI_TYPESAFE_API_KEY=... go test -run Live -v ./modules/decision`.
- A chat agent's `judge` settings have the decision service judge its group messages; they need the `decision` module on, and saving them while it is off is refused. `judge.wake` (`threshold`, default 0.7) answers a group message no reply or mention caught, and that does not reply to another module's message such as a card, when the judgment says it is addressed to the agent; when several agents pass, the surest answers. A message starting with the agent's keyword is judged too, in a group, since starting with a name is not always talking to it; with a mention, the keyword still picks the agent, and when the judgment fails (the decision service times out, is rate limited, or errs), the keyword triggers the agent as it would without `judge.wake`. Private chats and agents without `judge.wake` keep the keyword trigger. `judge.rules` says what else counts, or does not, as talking to the agent, such as its name also being a product people discuss. With it on, every such message in the agent's allowlisted groups is one decision request: about 2,200 input tokens with Jev (the last 10 messages, each but the judged one cut to 150 characters), about $0.09 per 1,000 group messages at $0.042 per million input tokens, and one `decision.completed` record holding those messages. To pick a threshold, replay a real chat kept outside the repository, one JSON object per line (`from`, `text`, and optionally `agent` for the agent's own messages and `addressed` true or false): `OTOGI_CHAT_REPLAY=chat.jsonl OTOGI_CHAT_REPLAY_AGENT=<name> OTOGI_TYPESAFE_API_KEY=... go test -run Replay -v ./modules/chat` prints each message's score and how many messages each threshold wakes.
- The `media` module (Media descriptions in the panel) describes the images, animations, and videos of people's new messages in the chats on its `describe` list, once per content (QQ names pictures by their MD5; other media is fetched and known by its SHA-256), so chat agents can read what they show. Its `steps` are the models it tries in order (`provider`, `model`, optionally `thinking`; `minimal` is enough): an error, a block, an answer out of format, or media the model did not get moves to the next. Configure at least two, since Gemini's free tier often answers 503 when busy, and on the free tier each model has its own daily limit. Use only providers whose model sees images and video: `deepseek-v4-pro` drops an image without saying so and answers as if it had seen one, so descriptions would be made up. `language` (default English) is what descriptions are written in; text on pictures and what videos say are copied as they are. Animations go to the model as six frames; media over 25 MiB is not described, which bounds memory rather than any API: a piece is held about 2.3 times over while it is described, and several can be described at once (QQ videos run about 1.7 MB per 21 seconds, so 25 MiB is some four minutes). Nor is a GIF that would take more than 80 MiB to decode, counted from its frame sizes before decoding: frames of one color compress about a thousandfold, so a small file can decode to gigabytes, and the message would be dispatched again after the process died. A GIF whose blocks do not read exactly as Go's image/gif reads them is not described either, since its count could not be trusted. eku's largest of 61 GIFs took 67 MiB. A description is kept in the module's database until the media goes unseen for 30 days. Each one is a `media.described` record with its token usage; each failed step is a `media.failed` record, and media left alone a `media.skipped` one. Live test against Gemini: `OTOGI_GEMINI_API_KEY=... go test -run Live -v ./modules/media`.
- Operators keep stickers, the pictures agents may send, with the media module's `/sticker` command: `/sticker add [note]` replying to a picture, or sent with one (in a private chat with the bot, that is how a picture is imported); `/sticker list`; `/sticker note <n> [note]`, an empty note clearing it; `/sticker remove <n>`. Only `operators` may use it, in chats on the `describe` list and in private chats. A reply finds a picture for two hours after it was sent, and on QQ a picture's link stops working after about an hour: send it again and add it at once. Only PNG, JPEG, and GIF pictures are kept, told by their content: Telegram's GIFs are MP4 files and are refused, and WebP is not kept yet. A sticker is at most 9 MiB, since QQ refuses uploads over about 10 MB and its driver uploads in one request; at most 50 are kept, 128 MiB in all, in the module's database. A sticker keeps its own copy of its kind and summary, so pruning descriptions leaves it alone; one with neither a summary nor a note is listed with a mark and is left out of what agents get until it has a note. Numbers are not reused after a removal. Each action is a `media.sticker` record.
- A chat agent's `media` settings have it read those descriptions; they need the `media` module on, with the agent's chats on its `describe` list. In the agent's recent messages, quotes, and wake judgment, media then reads as described (`[sticker: …]`, a screenshot with up to 300 characters of its text, `[video 0:12: …]`) instead of `[photo]`. With `as_text`, the current and the quoted message's media go to the model as descriptions instead of themselves, for a model that sees images poorly or not at all. A message waits for its own descriptions 10 seconds at most in all, before its judgment and, with `as_text`, before the reply, holding its worker meanwhile; a quoted message's media is described already or never will be, so it is not waited for. Media still undescribed reads as `[photo]`, and under `as_text` a `chat.media_skipped` record says why.
- The chat module's `people` list tells agents more about some people than the name the platform gives them; it is shared by every agent. Each entry's `user` is the platform (`qq` or `telegram`), a colon, and the person's sender ID: a chat's page in the control panel lists the people seen there under People, each with that ID below their name (`user:7C2E…`), so a person on QQ is `qq:user:7C2E…`. On QQ a person's ID is the same in every group and private chat, so one entry covers them everywhere; the same person on Telegram is another entry. Saving a `user` that is not platform:ID, or one listed twice, is refused. `name` is what agents call them: wherever a model is told who sent a message, judgments included, it reads `name (the platform's name)`, since people mention them by the name the platform shows; the transcript keeps the platform's names, so a change applies at once to the recent messages and judgments, which are read from it each time, while a thread's earlier turns keep the names they were sent with. `note` says who they are: the notes of the people in a request, its sender, whom they quote, and the recent messages shown, lead it under "About people here", in that request only. `threshold_factor` (0.1 to 10, default 1) multiplies the judgment thresholds of their messages: at 0.9, a 0.7 threshold wakes an agent at 0.63; a factor that takes an agent's threshold past 1 leaves their messages unjudged for it (each one gets a `chat.unjudged` record saying so), so judgments never wake it for them, while mentions and replies still do.
- A Telegram account's `upload_threads` (default 8) is how many parts of a file it uploads at once. Each part waits for Telegram's answer, so one at a time is slow far from the account's data center (about 450 KB/s from Los Angeles).
- `otogi validate` checks a config file without starting drivers or touching data. It checks the file only: the settings edited in the panel were checked when they were saved.
- The control panel is served by the bot at every path outside `/api/`, from the build embedded in the binary (`web/`), when `management.public_url` names where it is reached. Put a TLS reverse proxy in front that passes the whole site to `management.addr`, keeping `Host` and setting `X-Forwarded-For` (nginx: `proxy_pass http://127.0.0.1:8383; proxy_set_header Host $host; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`). Sign-in goes through an OpenID Connect provider: register a confidential client there with the redirect URI `<public_url>/api/auth/callback` and the post-logout redirect URI `<public_url>/sign-in`, then set `management.oidc` (`issuer`, `client_id`, `client_secret` as a `${VAR}` reference, and `allow`, the provider usernames that may sign in).
- What a change needs depends on where the setting is. The general settings, the language model providers, the modules, the allowlists, and the secrets apply when they are saved, without a restart. The platform accounts and the process settings are saved in the panel and apply at the next start, which `POST /api/restart` asks for. What is in `otogi.yaml` (the data directory, the management API and sign-in) is read at startup: changing it means editing the file on the server and restarting.

## Data directory

```text
<data>/
  eventlog.sqlite                 # event log, and the directory of chats seen
  panel.key                       # the key that seals the control panel's session cookies
  modules.sqlite                  # module key/value state and timers, settings, secrets set in the panel
  modules/<id>.sqlite             # a module's private database, if it uses one
  telegram/<account>/session.json # gotd session (login)
  telegram/<account>/state.sqlite # inbox, update state, send records
```

Each Telegram account has its own session and database. The database records which account it belongs to, and startup refuses a database that belongs to another account, which prevents mixing up accounts.

## SQLite

- WAL mode, `synchronous=NORMAL`, a busy timeout, and foreign keys on, all set when opened.
- Each owning component embeds its migrations and applies them forward-only at startup. A database newer than the binary is refused.
- Never copy a live database file; use the backup methods below.

## Backup and restore

**Backup**
- Bot stopped: copy the data directory.
- Bot running: for each database, run `sqlite3 <db> ".backup <dest>"` (or `VACUUM INTO`), and copy the session files.

**Restore**
1. Stop the bot.
2. Put the files back in the data directory.
3. Start the bot.

Telegram fetches any updates newer than the restored state. A backup holds what the data directory holds: the session files, the messages in the event log, and, in `modules.sqlite`, the secrets set in the control panel as given. Keep it as the data directory is kept, readable only by the service user. Encryption and off-host storage of backups are up to the operator.

## Upgrades

1. Back up.
2. Replace the binary and restart. Migrations run at startup.
   The first start of a binary that keeps the accounts and the process settings in the panel saves the file's `telegram`, `qq`, `kernel`, `log.format`, and `shutdown_timeout` as the first revisions of `accounts` and `process`, and runs with them; nothing needs doing first, and Telegram sessions stay where they are. From then on those keys are changed in the panel, and can be removed from the file.
3. To roll back, restore the backup taken before the upgrade if the new binary migrated a schema; otherwise just swap the binary back.

Upgrading gotd also changes the Telegram API layer. Follow the gotd upgrade steps in the [Telegram runbook](runbooks/telegram-mtproto.md#gotd-upgrade).

## Signals and exit codes

- SIGINT or SIGTERM starts graceful shutdown (see `runtime.md`); a second signal forces exit.
- Exit 0 means a clean stop: a signal, or `POST /api/shutdown`. The supervisor leaves the process stopped.
- Exit 75 means a restart was requested with `POST /api/restart`: the process stopped as cleanly as for exit 0, and is to be started again. The supervisor's rule of restarting on a non-zero exit does that; the panel's restart button relies on it. The `process.state` records of that stop carry `restart_requested_by`. If the process does not come back, start it on the server.
- Any other non-zero code means a startup failure, a component failure, or a forced stop, and the reason is printed on stderr.

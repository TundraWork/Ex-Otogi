# Extensions

## Model

Modules and drivers are Go packages compiled into the binary and registered explicitly in `cmd/otogi`. There are no dynamically loaded plugins. Flexibility comes from a rich, stable SDK in `pkg/otogi`: a module written once works on every platform the event model covers, and new modules need no kernel changes.

## Modules

A module implements bot behavior. It:

- declares its identity, subscribed actions, ordering, and timeout in a `ModuleDescriptor`;
- handles each event through `Handle(ctx, event, invocation)` and returns an error or nil;
- acts only through capabilities on its `Invocation` (send, send elsewhere, edit, delete, react, fetch media);
- never imports platform SDKs, kernel internals, or another module's package.

### SDK

The module SDK is delivered in steps:

- messaging: send, send to other conversations, reply and quote (relations), edit, delete, react, send and fetch media (implemented);
- streamed messages: `Invocation.Stream` shows a message while it is still being written, such as a language model's reply. The module passes the whole content so far to `Update` and the final content to `Close`; the driver decides how the platform shows it. Telegram shows "typing" for as long as the reply is being written, and the reply as a live draft (bot accounts, private chats) or as a message edited as it grows (user accounts, and everywhere else), continuing in new messages past its limits. QQ streams a private-chat reply in one message that grows, within QQ's reply window, and finishes it as ordinary messages if QQ refuses a chunk or the reply outgrows one message; QQ groups cannot stream and get the final content. Drivers implement `otogi.Streamer`; without one, the kernel sends the final content on `Close`;
- commands and filters declared in the descriptor (implemented): a declared command goes only to its module, and modules receive incoming events only unless their filter opts in to outgoing or system events. The bot's own messages are outgoing events; QQ pushes none of them, so its driver queues each message it sends, in groups and private chats, as the bot's own, at the time QQ gives it, and keys it as a push would be, so it is kept once. Every module also has an "ignore bots" switch, kept and applied by the kernel like allowlists (`Kernel.SetIgnoreBots`, stored in `modules.sqlite`): while it is on, which it is unless the operator turns it off, no event from a bot account reaches the module. Drivers set `Actor.Bot` from the platform's own flag (a Telegram bot user, a QQ bot author); userbots, people's accounts a program drives, are not told apart. With the switch off, the chat module keeps bots' messages as context, but a bot never triggers an agent, so two bots cannot answer each other forever;
- per-module key/value store, private SQLite database, `Starter`/`Stopper`, and typed config (implemented; see `modules/notes`);
- cron jobs, persistent timers, and typed services shared between modules (implemented; see `modules/reminders`);
- names: events carry the names drivers know (`Conversation.Title`, `Description`, `Members`, `Actor.Name`). Before modules see an event, the `names` middleware fills in from the chat directory what the driver left out: a chat by the name the operator gave it in the panel (which wins), else the platform's latest title, and a sender by the latest name they were seen with; in a private chat, the other person is called what the chat is;
- allowlists (implemented; see `modules/twitter`): a module that answers only in chats the operator chooses declares its lists in `Allowlists` and asks `Host.Allowed(list, e.ChatKey())`. The kernel keeps the lists and answers from memory. A list that grants another module's capability names it in `About`, as the chat module's lists of where agents may use a module's tools do;
- language models: a module whose config names a provider (`provider: gemini`, or the name of an OpenAI-compatible service such as `deepseek`, as the panel's language model settings have them; `model: ...`) gets it from the composition root's `llm` lookup when it is built, and is rebuilt when those settings change, and calls `Generate` with `otogi.Message` turns. A provider that can list its models also implements `llm.ModelLister`; the panel fetches the lists with it, never a module. `llm.Inline` fetches chat media for a prompt. Passing `Update` of an `Invocation.Stream` as the partial callback streams the reply into the chat. Keep each `Response.Turn`, `Native` included, to continue the conversation: the provider resends its own turns exactly, which keeps the model's hidden reasoning and generated images intact. `llm.Run` adds tools: provider built-ins (`web_search`, the provider's own search; `url_context`; `code_execution`) and functions that modules offer as `llm.Tool`s through the service `llm.ToolsService(<module>)` (`llm.tools/<module>`); it runs the model's calls round by round and streams the reply across rounds. Its `say` callback, if set, takes what the model first says in a round that also calls functions, before the calls run, and the reply then starts over: the chat module sends those words as a message of their own, so where nothing streams, such as a QQ group, they do not wait for the calls, and the rest of the reply, words before later calls included, follows in one more message. A tool made with `llm.NewEndingTool` ends the reply: when every call in a round ran, is to such a tool, and succeeded, `Run` returns after their results without asking the model again; the chat module's `send_sticker` is one. `reminders` (`set_reminder`), `notes` (`add_note`, `list_notes`), and `todou` (read and work the todou projects linked to the chat) offer tools: a module provides `[]llm.Tool` from `Start` under the name it lists in `Provides`. The chat module's `tools` names the modules whose tools agents may use, and each gets an allowlist, `tools:<module>`: agents get a module's tools only in the chats on it. A profile's own `tools` are the built-ins, offered wherever it answers.
- decisions: a module that asks yes/no questions about a conversation lists `decision.Service` (`decision`) in `Requires` and gets a `decision.Decider` with `otogi.Lookup` in `Start`. `Decide` takes a state, sent as JSON, and questions keyed by IDs the module chooses, each its whole text and, if set, what counts as yes and as no; it answers with the probability of yes for each, and a question left unanswered is missing. It does not retry: an error (`otogi.ErrInvalid` for a refused request, `otogi.ErrUnavailable` for timeouts, rate limits, and outages) is no decision, never a no. The `decision` module (Decisions in the panel) provides it, backed by TypeSafe Jev, and records every request. The chat module asks it for agents with `judge` settings;
- media descriptions: a module that reads what images, animations, and videos show lists `media.Service` (`media`) in `Requires` and gets a `media.Describer` with `otogi.Lookup` in `Start`. The `media` module (Media descriptions in the panel) describes the media of new messages in the chats on its `describe` list itself, once per content (by the driver's digest, such as QQ's MD5, or the SHA-256 of the bytes), trying its configured models in order, and keeps each description 30 days after the media was last seen. `Lookup` returns a kept description without waiting; a description's `Sticker` is the number of the kept sticker the media is, its `Summary` then the sticker's text, and 0 for other media; `Describe` waits until its context ends for the module to finish with the media, and fails at once with `media.ErrNotAllowed` or `media.ErrNotDescribed` for media it will not describe, and with `otogi.ErrUnavailable` when every model failed. The module also provides `media.StickersService` (`media.stickers`), a `media.Stickers`: the pictures operators keep with `/sticker`, which `List` gives by number with what each shows, and `Picture` as inline media ready to send (a GIF as an animation), failing with `media.ErrNoSticker` for a number not kept. The chat module sends them for agents given some in `media.stickers`: its own `send_sticker` only notes the pick, and chat sends the sticker after the reply, so no tool sends messages around chat;
- `modules/bilibili`: answers Bilibili video links in allowlisted chats with a card image (cover, title, uploader, counters, honors, description), drawn from an HTML template by chrome-headless-shell, started per card;
- `modules/twitter`: answers X post links in allowlisted chats with a card laid out like X's post page (author, badge, text, media grid, quote, poll, community note, time, views, counters), drawn the same way; posts come from FxTwitter, or X's embed endpoint when FxTwitter fails; a reply's card shows the post it replies to above it, as X's conversation does, with that post's pictures and quote (only that one post: the conversation is not followed further up); with `translate`, the card of a post not in Chinese also shows it translated by a language model, under the original, as X shows a translated post, and so its quote, the post it replies to, and that post's quote, each when it is not in Chinese. With `videos` (on unless turned off), a post's videos and GIFs follow its card as video media, each up to `max_video_mb` (default 50; from the embed endpoint, the encoding of highest bitrate that fits); a post whose pictures the card censors keeps them unless Content safety's `censored_videos` is on; drivers send them as the platform plays video (Telegram: a streamable video, a GIF as an animation). `modules/booth`: answers Booth item links with a card of the item's first still picture (a GIF may move and is passed over; videos are not in the gallery), name, shop, price and its options, wishes, tags, and description, from the item page's JSON; an R-18 item's picture is blurred enough to hide its details but not what it shows, and marked R-18. The card modules draw through `pkg/cardimage`, which also holds how a card shows a picture less than plainly, for every card to use alike: a `blurred` class for content its source marks sensitive (X's sensitive media, R-18 BOOTH items), and the `cover` sticker for a picture the platform refused. How far to blur, whether to cover and send a refused card again, and the sticker's image, opacity, and size are the `safety` module's settings (Content safety in the panel): it handles no events and offers them as the service `cardimage.ServicePictures` (`cardimage.Pictures`), which every card module requires, so changing them rebuilds the card modules with them;
- `modules/chat`: language model agents that answer keyword-led messages and replies to them in allowlisted chats, with the recent chat as context; an agent with `judge.wake` also answers the group messages no trigger caught that the decision service judges addressed to it, one request per message, and one with `judge.follow` those that carry on an exchange it is in, asked in the same request, the more it has followed up the surer the judgment must be; with `judge.wait` it waits in groups for the sender to finish, answering what called it meanwhile in one reply, in the `Handle` of the message that opened the batch, so the answer is that message's (a passive reply on QQ); a reply stops calling tools when less of its `timeout` is left than `tool_reserve` of its slowest model rounds (`llm.Limits`), and media over `max_media_mb` is named rather than shown; an agent with `media` reads the media service's descriptions where media was only named, and with `media.as_text` gets them instead of the media itself;
- formatted text: `otogi.RichText` builds annotated text, and `pkg/markdown` converts Markdown into it (see `modules/todou`) and back, for handing chat text to a language model.

Every effect names a slot; the kernel derives its idempotency key from the unit of work (event, job run, or timer run), the module, and the slot, so replays never repeat effects. Drivers receive effects through `otogi.Effector` and return `ErrUnsupported` for kinds they do not implement, and `ErrRefused` when the platform refuses the content for what it shows or says (QQ's moderation, code 40034006). The card modules (`twitter`, `booth`) answer a refused card by sending it once more with a see-through cover sticker over each picture; a card with no pictures is not sent again.

## Drivers

A driver adapts one IM platform. It:

- connects and authenticates to the platform;
- converts platform updates into rich events, keeping unknown platform data as extensions rather than dropping it;
- owns platform recovery (sequence state, catching up on missed history);
- implements outbound capabilities for its platform and translates platform errors into `pkg/otogi` errors;
- follows the component lifecycle in `runtime.md`.

A driver does not decide routing or module behavior.

## Configuration

Each module and driver has its own typed section in the main config file. Unknown fields are rejected so typos surface at startup. Defaults are documented next to the config struct.

The module convention: a `Config` struct and a `New(Config)` constructor in `modules/<id>`, plus one entry in `cmd/otogi/modules.go`. `Config` is the module's settings: `json` tags name the fields, and a `doc` tag on each describes it for the operator. The composition root generates the settings' JSON Schema from the type (with huma), validates saved settings against it, and decodes them strictly; schema tags such as `minimum` or `enum` add checks the panel can show. A `format` tag tells the panel what a value is, for its control: `markdown` (a long text, such as a system prompt), `text` (plain text of a few lines, in a box that grows with it), `id` (a number that is an identifier, typed without stepping), `tool-module` (on a list: modules that offer agents tools, the service `llm.tools/<id>`, as `GET /api/modules` lists them, those off marked), `llm-provider` (a language model provider's name: a choice of those set), `llm-model` (a model ID of the provider the field named `provider` in the same object names: a search of that provider's fetched models, free text allowed), and `llm-thinking` (a thinking level of that object's `model`, whose unsupported levels are marked); the composition root's tests check that every `llm-model` and `llm-thinking` field has its `provider` beside it. The choices only help: the constructor still decides what saves, and a saved value no longer among them is shown, flagged, to remove. Three tags are for the panel alone: `unit:"MB"` is shown after a number, `placeholder:"telegram/{account}/session.json in the data directory"` is the default of a field that depends on the fields beside it, whose values fill in its `{names}` (a static default is the `default` tag), and `ordered:"true"` lets the operator move a list's items, where their order is what the module does (media's steps, chat's profiles); the served schema has them as `x-unit`, `x-placeholder`, and `x-ordered`. A duration field's `doc` need not convert it: the panel says how long it is. Durations are `otogi.Duration` (`"5m"`), and secrets `otogi.Secret`, which holds a `${NAME}` reference that `Resolve` resolves with the lookup the composition root passes to the constructor (the secret set in the panel, or else the environment variable of that name). The constructor validates the rest and does no I/O: it runs on every save, before the module starts. It refuses a value with an `otogi.SettingError`: the setting's path in the schema's notation (`profiles[0].provider`, `agents.main.token`) and the reason, such as the error `Resolve` or the provider lookup returned. Several, joined with `errors.Join`, each keep their path, and the panel shows each at its field, as it shows a value that breaks the schema. Return them as they are: one wrapped in more words is shown whole, at no field. The operator turns modules on and off at runtime.

## Operators

The general settings' `operators` list platform-qualified actor IDs (`telegram:user:123`, exactly as `/whoami` prints them). The composition root hands modules that gate commands a function returning the list as it is now, which they call for each command, so a change in the panel applies without rebuilding them; a denied user is told their ID.

The bot's accounts are its own, so their outgoing messages are what the bot sent: the command parser never reads a command in them, and they never count as an operator. A module's replies therefore cannot invoke commands, whatever they say.

## Failure isolation

A module panic, error, or timeout affects only that delivery. It is recorded with the module identity, and other modules still receive the event.

## Middleware

Middleware runs on every event before modules, in registration order, and may modify or drop it. It is where cross-cutting policy goes: allowlists, sleep mode, rate limits, command parsing. It must be fast.

## Compatibility

The SDK is unstable while `next` is in development. Breaking changes update all in-tree modules in the same change. There is no compatibility with `master` modules.
